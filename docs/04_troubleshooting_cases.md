# 트러블슈팅 사례

## 사례 1. 레거시 장비 라우팅 / NAT 통신 불가

### 문제
- 레거시 장비가 VPN에는 연결되지만 외부 관리망에서 내부 터널 IP로 접근이 되지 않는 문제가 발생했습니다.

### 원인
- Legacy 대역에 대한 SNAT / FORWARD / direct rule 적용이 일반 SG와 다르게 구성되어 있었고,
- tun 인터페이스와 PTP 게이트웨이 기준이 맞지 않아 패킷이 터널로 전달되지 않았습니다.

### 해결
- Legacy 전용 대역과 게이트웨이를 기준으로 FORWARD / SNAT / firewalld direct rule을 별도로 정리했습니다.
- server-legacy 설정, CCD, 라우팅, 상태 로그 기준을 분리해 혼선 없이 운영되도록 구조화했습니다.

### 결과
- 레거시 장비 통신 경로가 일반 장비와 충돌하지 않도록 정리되었고, 장애 분석 속도도 빨라졌습니다.

## 사례 2. 재부팅 후 운영 상태 불일치

### 문제
- 서버 재부팅 이후 OpenVPN 서비스는 올라왔지만 인터페이스, 라우팅, 방화벽 규칙 일부가 누락되어 운영 이상이 발생할 수 있었습니다.

### 원인
- 서비스 기동 순서와 네트워크 규칙 적용 상태를 한 번에 검증하는 체계가 부족했습니다.

### 해결
- Runtime Guard를 도입해 서비스, 인터페이스, firewalld/direct rule, 보조 스크립트 실행 상태를 재부팅 후 자동 점검하도록 구성했습니다.

### 결과
- 재기동 이후 운영 상태를 자동으로 확인할 수 있게 되었고, 운영자가 수동으로 재점검해야 하는 부담이 줄었습니다.

## 사례 3. 운영 서버와 로컬 기준선 불일치

### 문제
- 운영 중 즉시 수정된 스크립트나 API 로직이 로컬 검증본과 달라지는 경우, 이후 유지보수 시 혼선이 발생할 수 있었습니다.

### 원인
- 운영 서버 반영본과 로컬/검증 환경 간 동기화 기준이 명확하지 않았습니다.

### 해결
- 운영 서버 소스를 직접 비교 기준으로 삼아, 실제 변경된 파일만 선별해 로컬과 minimal 환경에 반영하는 절차를 정리했습니다.

### 결과
- 운영 반영본을 기준으로 유지보수 기준선을 맞출 수 있게 되었고, 이후 수정 이력 관리가 쉬워졌습니다.
